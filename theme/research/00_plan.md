# 研究テーマ選定 採点計画

軸の一覧（記号・群・名前）の正本は `axes.csv`。解説と出典は `theme/paper/main.tex`（ポータルの「テーマをどう選ぶか」）。軸を見直した経緯は `axes_review.md`。ここは採点する人・エージェントのための作業手順である。

## 問い

AI に大量の論文を読ませ、テーマと仮説を大量に出させ、人が選ぶ。そういう小さなチームが、
経済学・計量経済学で**最初にどのテーマを選ぶべきか。**
成果は、学会で発表でき査読論文になること。または、データ分析に有用なライブラリとして公開できること。

## 3つのトラック

テーマには必ずトラックを1つ付ける。軸は共通だが、読み替えが要る軸がある（下の表）。

| トラック | 記号 | 何をする研究か | 典型的な成果 |
|---|---|---|---|
| 因果推論・実証 | `causal` | 政策や出来事の効果を、外生変動を使って推定する | 実証論文 |
| 構造推定 | `structural` | 経済モデルのパラメータを推定し、反実仮想を計算する | 実証論文＋推定コード |
| 推定量・計量手法 | `method` | 新しい推定量・検定・計算手法を作り、性質を示す | 手法論文＋ライブラリ |

## 採点軸（各 1–5 の整数。5 が「このチームにとって有利」）

アンカーに従って採点し、迷ったら低い方を付ける。根拠（数値・出典 URL）を必ず短く書く。

| 群 | 記号 | 軸 | 5 | 3 | 1 |
|---|---|---|---|---|---|
| 問いの価値 | Q | 重要度 | 答えが出ると、分野外の経済学者や実務家の判断も変わる | 分野内では重要 | 誰の判断も変わらない |
| | N | 新規性（文献の空白）※ | 信頼できる答えがまだ無い、または既存の結果が割れている | 既存研究に明確な穴がある | 同じ設計の研究が既に複数ある |
| | R | どちらの結果でも知見になるか | 効果があっても無くても（手法なら、勝っても負けても）論文になる | 片方の結果だけが論文になる | 「うまくいったときだけ」面白い |
| | T | メカニズムを確かめられるか | 競合する説明を、手元のデータで判別できる（異質性・中間の結果変数・別の設計） | メカニズムを示唆する証拠は出せるが、判別はできない | 効果の有無しか言えない |
| 信頼性 | I | 識別・推論の信頼性 | 仮定が明確で、反証テストやシミュレーションで点検できる | 仮定に議論が残る | 主張を支える手がかりが無い |
| | W | 検出力・精度 | 文献から見て妥当な大きさの差を、十分な確率で検出できる | 大きめの差なら検出できる | 妥当な差は検出できない |
| | E | 外的妥当性・適用範囲 | 複数の文脈・データで成り立つ、または使える場面が広い | 一般化に追加の仮定が要る | 特殊な標本・設定に限られる |
| 実行可能性 | D | データ入手性※ | 公開データ（手法なら合成データと公開の再現データ）で今日から始められる | 申請・購入で1〜3か月 | 入手の見込みが立たない、または1年以上 |
| | X | 検証ループ速度 | 推定・シミュレーションのやり直しが数日以内 | 数週間〜数か月 | 年単位 |
| | L | 倫理・法務・再現の低リスク | 公開データで、再現パッケージを全部公開できる | 規約の確認や倫理審査が要るが定型の手続き | 秘匿性が高く、公開にも AI の利用にも強い制約がある |
| | F | AI 増幅度 | 律速が、AI の得意な工程（文献の整理・データ構築・標準的な推定・頑健性の確認・シミュレーション）にある | 半々 | 律速が、AI の苦手な工程（新しいデータ源の開拓・制度の深い理解に依る着想・利用許可・現地調査）にある |
| 競争と出口 | C | 競合の空白度 | 同じ問いを追う進行中の研究・既存ライブラリが見当たらない | 数チーム・数個ある | 有力チームの論文や定番ライブラリが既にある |
| | U | 独自の資産 | 自分たちで作る新しいデータ・コードが、次の研究にも使える資産になる | 既存のものの新しい組合せ | 誰もが持っているものだけ |
| | O | 出口の明確さ | 出したい学会・査読誌が具体的に言え、その基準に届く見込みがある | 分野の学会・ワークショップなら見込める | 受け手が思い当たらない |
| | S | ライブラリ価値 | 他の研究者が自分の研究で繰り返し使う道具になる | 再現パッケージとして使われる | この論文でしか使わないコード |

※ **根拠の欄が空なら、上限2点で計算する。**

- **N（新規性）**: `nearest` 欄に、いちばん近い既存研究を3本挙げ、それぞれとの差を1行ずつ書く（例: `id: 差 / id: 差 / id: 差`。id は文献マスター表 `literature/papers.csv` のもの。表に無ければ先に足す）。AI は自分のアイデアを新しいと思いがちで、自己評価は当てにならない。印象では付けない。
- **D（データ入手性）**: `data_check` 欄に、データの名前・入手手順・必要な変数があることの確認（公開の変数一覧の URL など）を書く。データを見てから問いを作ると、実行できる問いが大きく増える。
- 再採点は、採点したのと別の系統のモデルで行う。上位10個の N は、人が確かめる。

### トラックごとの読み替え

| 軸 | 因果推論 | 構造推定 | 推定量・手法 |
|---|---|---|---|
| T | 効果の経路を、異質性や中間の結果変数で確かめられる | モデルのどの仕組みが結果を生むかを、反実仮想で切り分けられる | なぜ既存手法より良いのかを、理論かシミュレーションで説明できる |
| I | 無作為化や制度由来の外生変動があり、反証テストができる | どの変動がどのパラメータを決めるか説明でき、使っていないデータで当てはまりを確かめられる | 理論的な保証（一致性・被覆率）があり、シミュレーションで確かめられる |
| W | 妥当な効果を検出できる標本 | パラメータが精度よく決まる。反実仮想の幅が結論を出せる狭さ | 既存の手法との差が、現実的な標本サイズで測れる大きさ |
| E | 他の文脈・時期にも当てはまる | 政策が変わってもモデルの前提が保たれる | 使える場面が広い（データの形・標本サイズ・分野） |
| D | 実データの入手 | 実データの入手（モデルを決めるのに要る変動を含むか） | 合成データと、公開されている再現データで足りるか |
| X | 推定のやり直しにかかる時間 | 1回の推定にかかる計算時間 | シミュレーション1周にかかる時間 |

### 参考列（合計点には使わない）

- K: 分野全体の混雑度（1–5。5=研究者・利用者が非常に多い）。読み手・査読者・ライブラリの利用者の厚さを表す。C（同じ問いの競合）とは別に評価する。星取り表の詳細に出すだけで、計算には使わない。

## 群の点・合計点・選ぶときの条件

- **軸に重みは付けない。** 目標ごとに重みの型を用意する方法は、やめた（2026-11-14）。重く見たい項目があれば、星取り表でその群や軸の順に並べ替えて直接見る。
- **群の点** = 群に属する軸の平均 × 20（20〜100点）。星取り表は、この4つの点を主に見せる。15軸は内訳として畳む。
- **合計点** = 4群の点の幾何平均。掛け算なので、1つの群が弱いと全体が下がる。足切りは別に置かない。
- 数点の差には意味がない。
- **選ぶときの条件（上位10個の組合せ）**: 点の順に上から10個を取らない。AI に任せると、設計が差の差に偏り、似たテーマが並ぶ。
  1. 同じ設計（`design` 列。例: 差の差）は4個まで。
  2. 3つのトラックから、少なくとも2個ずつ入れる。
  3. 似たテーマ（同じデータ・同じ制度）は1個にまとめる。

## 定性情報（自由記述、各1–2文）

- design: 設計の短い名前（選ぶときの条件で、同じ設計を数えるのに使う。例: 差の差、回帰不連続、需要推定、測定誤差）
- field: JEL 分類（例: J31, C23）と主な分野
- design_type: 想定する設計（RCT／差の差／回帰不連続／操作変数／構造推定の種類／推定量の種類 など）
- data_sources: 使うデータの名前、秘匿区分（T0/T1/T2）、入手手順
- competitors: 近い問いを追うチーム・論文・既存ライブラリ
- lit_trend: 直近3年の研究動向
- first_project: このチームが最初の6か月でやるなら何か（1文）
- risks: 主なリスク（1文）
- sources: 根拠 URL（`;` 区切り、2–5件）
- rationale: 軸の根拠を「Q:… / N:… / …」の形で簡潔に
- win_thesis: このチームが勝てる理由／勝てない理由を1–2文
- status: `pilot`（事前知識だけで採点。出典未調査）／`screened`（一次採点。点は AI の事前知識。近い既存研究は書誌を照合し、データは所在だけ確認）／`scored`（テーマごとに出典を調べて採点）／`calibrated`（ブラインド再採点で補正済み）

## 出力

`theme/research/themes.csv`（UTF-8）。列:

```
id,track,design,cluster,theme,Q,N,R,T,I,W,E,D,X,L,F,C,U,O,S,K,status,nearest,data_check,field,design_type,data_sources,competitors,lit_trend,first_project,risks,sources,rationale,win_thesis
```

```sh

python3 tools/build_themes.py theme/research/incoming/<名前>_themes.tsv theme/research/incoming/<名前>_data.tsv
python3 tools/score_themes.py            # theme/research/scored.csv を書く

python3 portal/build.py                  # ポータルの「星取り表」に反映
```

## 甘辛の補正（ブラインド再採点）

採点者（エージェント）ごと・クラスタごとに甘辛が出る。元のラボでは、上位ほど楽観的に採点されていた。

1. 別のエージェントに、テーマ名と定性情報だけを渡して再採点させる（元の点は見せない）。結果は `calibration/blind.csv`。
2. クラスタごと・軸ごとに、元の点と再採点の差の平均を出す。差が0.5点を超える所は、人が見て直す。
3. 直した記録を `calibration/notes.md` に残し、status を `calibrated` にする。
